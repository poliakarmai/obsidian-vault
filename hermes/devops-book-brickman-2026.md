## ЧАСТЬ I — РАЗВЁРТЫВАНИЕ

### ПРИНЦИП 1. Эволюция развёртывания: локально → облако

Стек зрелости деплоя:
```
Локально (localhost:3000)
  → Сервер (ssh + scp + systemd)
    → PaaS (Render/Heroku: git push)
      → IaaS (AWS EC2: полный контроль)
        → Контейнеры (Docker + K8s)
          → Serverless (Lambda: нет серверов вообще)
```

**Правило:** начинай с самого простого уровня, поднимайся когда перерастаешь. PaaS экономит 80% времени на старте.

**Сравнение IaaS vs PaaS:** IaaS даёт контроль (сеть, диски, sécurité), PaaS — скорость (не думаешь о серверах). Для продакшена — IaaS, для прототипа — PaaS.

---

### ПРИНЦИП 2. Инфраструктура как код (IaC): 4 уровня зрелости

| Уровень | Инструмент | Плюсы | Минусы |
|---------|-----------|-------|--------|
| 1. Ad-hoc скрипты | Bash | Быстро | Не идемпотентны, нет состояния |
| 2. Управление конфигурацией | Ansible | Идемпотентность, шаблоны | Только конфигурация, не ресурсы |
| 3. Шаблонизация сервера | Packer | Immutable инфраструктура | Долгая сборка образа |
| 4. Выделение ресурсов | OpenTofu/Terraform | Декларативно, state, план | Кривая обучения |

**Золотое правило:** Resource provisioning (OpenTofu) + Config management (Ansible) + Server templating (Packer) = идеальный CI/CD пайплайн.

**Ключевые критерии IaC:** идемпотентность, декларативность, версионирование, автоматизация, тестируемость.

---

### ПРИНЦИП 3. Оркестрация: от серверов к контейнерам и serverless

| Слой | Инструмент | Паттерн |
|------|-----------|---------|
| Серверы | Ansible | Rolling update, health checks, rollback |
| ВМ | Packer + ASG | Immutable infra, auto-scaling, ALB |
| Контейнеры | Docker + K8s | Pod, Deployment, Service, Ingress |
| Serverless | AWS Lambda | API Gateway, zero-ops |

**Стратегии обновлений:**
- **Rolling:** по одному серверу, медленно, безопасно
- **Blue-green:** две среды, мгновенное переключение, двойной ресурс
- **Canary:** 5% трафика → проверка → 100%, лучший баланс риск/ресурс

**Контейнеры побеждают:** Docker — стандарт упаковки. K8s — стандарт оркестрации. EKS/GKE — не управляй сам, бери managed.

## ЧАСТЬ II — РАЗРАБОТКА

### ПРИНЦИП 4. Контроль версий: trunk-based и фича-флаги

**Рекомендации Брикмана:**
- **Trunk-based development** — короткоживущие ветки (часы, не дни)
- **Feature flags** — мёржим в main, включаем когда готово
- **Conventional commits** — `feat:`, `fix:`, `chore:`
- **CODEOWNERS** — явное владение кодом
- **.gitignore до коммита** — ни одного секрета в репо

**Правило Брикмана:** «Если ветка живёт больше дня — ты делаешь что-то не так. Либо задача слишком большая, либо ты не используешь фича-флаги.»

---

### ПРИНЦИП 5. Тестирование: пирамида, а не рожок

```
       /\
      /E2E\         ← мало, медленно, хрупко
     /------\
    /Integr. \      ← средне
   /----------\
  / Unit tests \    ← много, быстро, надёжно
 /--------------\
```

- **Unit-тесты:** >70% покрытия, <10ms каждый
- **Интеграционные:** БД, API, внешние сервисы
- **E2E:** критический путь пользователя
- **Инфраструктурные тесты:** `OpenTofu validate`, `ansible-lint`, `Packer inspect`

## ЧАСТЬ III — ДОСТАВКА

### ПРИНЦИП 6. CI/CD: конвейер, а не набор скриптов

**Архитектура пайплайна (GitHub Actions):**
```
Push → Build → Test → Staging Deploy → Staging Test → Production Deploy
         ↓        ↓          ↓               ↓               ↓
      Lint    Unit      Canary 5%      Smoke test     Rollback ready
```

**Стратегии деплоя (выбор Брикмана):**
- Staging: **Rolling** (медленно, дёшево)
- Production: **Canary** (5% → мониторинг 10 мин → 100%)

**Креды в CI/CD:**
- ❌ Долгоживущие токены в secrets
- ✅ OIDC — временные креды (GitHub Actions → AWS IAM без секретов)

---

### ПРИНЦИП 7. Мульти-окружение: аккаунты, не environment-переменные

**Ошибка:** `if env == "prod"` в коде.
**Правильно:** отдельный AWS-аккаунт на среду. Полная изоляция.

```
aws_accounts/
├── dev/       (свободная песочница)
├── staging/   (копия прода, интеграционные тесты)
└── prod/      (жёсткий IAM, MFA, CloudTrail)
```

**Монорепо vs полирепо:**
- Стартап < 5 чел → монорепо
- 5-20 чел → монорепо + CODEOWNERS
- >20 чел → полирепо по доменам

## ЧАСТЬ IV — ИНФРАСТРУКТУРА

### ПРИНЦИП 8. Сеть: zero trust, не «замок и ров»

**Модели безопасности:**
- ❌ **«Замок и ров»:** внутри периметра — всё доверено. Один прокол = всё.
- ✅ **Zero trust:** каждый запрос аутентифицируется. mTLS между сервисами.

**Практика:**
- VPC + приватные подсети (нет публичных IP)
- VPN для доступа (WireGuard)
- Service mesh (Istio/Linkerd) для mTLS между подами
- DNS: Route53, внешние домены через регистратора

---

### ПРИНЦИП 9. Безопасность: секреты, TLS, шифрование

**Управление секретами (по нарастающей):**
1. env-файлы → ❌ (в репо попадают)
2. CI/CD secrets → нормально для CI
3. Secrets Manager (AWS/GCP) → ✅ ротация, аудит, версионирование
4. Vault (HashiCorp) → продвинуто: динамические секреты

**TLS:**
- Let's Encrypt для внешнего HTTPS
- Внутренний mTLS через service mesh
- HSTS-заголовок (никогда не http)

**Шифрование:**
- At rest: AES-256 (включено по умолчанию в AWS S3/RDS)
- In transit: TLS 1.3 минимум
- End-to-end: Signal/WhatsApp-паттерн

### ПРИНЦИП 10. Данные: правильная БД под задачу

| Задача | База |
|--------|------|
| Транзакции, связи | PostgreSQL (реляции, ACID) |
| Кеш, сессии | Redis (key-value) |
| Файлы, бэкапы | S3 (объектное хранилище) |
| Поиск, логи | Elasticsearch / OpenSearch |
| Аналитика | ClickHouse / BigQuery (колоночные) |
| Очереди | RabbitMQ / SQS |
| Потоки | Kafka |

**Резервное копирование:**
- RPO (точка восстановления): 1 час для прода
- RTO (время восстановления): 4 часа
- Автоматические снепшоты + реплики read-only
- **Тестируй восстановление раз в квартал!**

---

### ПРИНЦИП 11. Мониторинг: логи + метрики + трейсы + алерты

**3 столпа наблюдаемости:**
1. **Логи** — структурированные (JSON), агрегация (ELK/Loki)
2. **Метрики** — RED (Rate, Errors, Duration) + USE (Utilisation, Saturation, Errors)
3. **Трейсы** — распределённая трассировка (Jaeger/Tempo)

**Алерты (правило Брикмана):**
- На каждый алерт — runbook (что делать)
- PagerDuty/Opsgenie для эскалации
- **Silence when OK, alert when broken**
- Проверяй что алерты вообще доходят (раз в месяц — тестовый)

**SLO/SLI:**
- Доступность: 99.9% (8.7 ч даунтайма в год)
- Латентность: p95 < 200ms
- Error rate: < 0.1%

## ЧАСТЬ V — БУДУЩЕЕ

### ПРИНЦИП 12. Будущее DevOps: без инфраструктуры, GenAI, платформы

**Брикман выделяет 5 трендов:**

1. **Без инфраструктуры** — serverless 2.0: Cloudflare Workers, Deno Deploy
2. **Генеративный ИИ** — AI-ассистенты для кода, тестов, деплоя
3. **Безопасно по умолчанию** — фреймворки с built-in CSP, CORS, rate limiting
4. **Платформенная инженерия** — Internal Developer Platform (IDP)
5. **Будущее IaC** — от HCL/YAML к реальным языкам (Pulumi, CDK, Wing)
